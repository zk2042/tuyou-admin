# 项目开发手册

## 1. 项目定位

本项目基于 `@umijs/max`、`Ant Design`、`Redux Toolkit`、`react-redux` 搭建，适合中后台管理系统开发。

当前项目约定如下：

- 路由和框架配置使用 `config/` 目录维护
- 页面级 UI 放在 `src/pages/`
- 接口请求代码放在 `src/services/`
- 全局初始化数据使用 `getInitialState`
- 当前登录用户、布局用户区、权限入口统一依赖 `getInitialState`
- 应用运行期的全局共享状态使用 `Redux Toolkit`
- 业务层不再新增 `Umi model`
- 当前登录态仍为前端 mock + 本地缓存方案，待后端接口接入后替换

## 3. 目录说明

```text
config/
  config.ts         Umi 主配置
  routes.ts         路由配置
  proxy.ts          代理配置

src/
  app.tsx           Umi 运行时配置、Provider 挂载、初始化数据、布局用户区
  access.ts         权限定义
  pages/            页面目录
  components/       公共组件
  services/         接口调用层
  store/            Redux Toolkit 状态管理
  constants/        常量
  utils/            工具函数
```

### 推荐职责划分

- `config/` 只放框架层配置，不写业务逻辑
- `pages/` 负责页面组装，不直接堆复杂请求逻辑
- `services/` 负责接口定义和请求封装
- `store/` 负责跨页面、跨组件共享的运行期状态
- `components/` 放复用组件，尽量避免依赖具体页面

## 4. 配置说明

### 4.1 Umi 主配置

文件：`config/config.ts`

主要负责：

- 开启 `antd`
- 开启 `access`
- 开启 `initialState`
- 开启 `model`
- 开启 `request`
- 注入路由配置
- 注入代理配置

补充说明：

- 虽然业务层统一使用 `Redux Toolkit`，不再新增 `src/models/*`，也不在页面中使用 `useModel`
- 但只要项目开启了 `initialState`、`access`、`layout` 等 Umi 内置能力，Umi 生成的临时代码仍会依赖 `plugin-model`
- 因此 `config/config.ts` 中需要保留 `model: {}`
- 这里保留的是框架层依赖，不代表团队重新回到业务 `model` 方案

### 4.2 路由配置

文件：`config/routes.ts`

约定：

- 所有页面路由统一在这里维护
- 页面组件使用 `component: './Home'` 这种相对 `src/pages` 的写法
- 路由变多后，可继续拆成多个路由文件再聚合导出

### 4.3 代理配置

文件：`config/proxy.ts`

当前按环境预留了以下配置入口：

- `development`
- `test`
- `pre`
- `production`

本地联调时，优先在 `development` 中补充代理规则。

## 5. 运行时入口

文件：`src/app.tsx`

这里承担 4 件事：

### 5.1 获取全局初始化数据

通过 `getInitialState()` 获取应用启动阶段需要的数据，例如：

- 当前登录用户
- 权限基础信息
- 系统级配置
- 默认租户信息

当前项目里，`getInitialState()` 主要用于提供布局和权限所需的当前用户信息。

注意：

- 现阶段没有接真实“当前用户”接口
- 默认使用前端 mock 用户，并写入本地缓存作为开发期演示数据
- 后端联调后，应替换为“有 token 才请求当前用户信息”的正式逻辑

### 5.2 挂载 Redux Provider

通过 `rootContainer()` 将 Redux 的 `Provider` 挂到应用根部，确保所有页面都可以访问 store。

### 5.3 注入 antd App 实例

通过 `rootContainer()` 包裹 `App`，并在内部桥接 `App.useApp()` 的实例到 `utils/message`。

这样做的目的是：

- 让请求拦截器、全局错误处理等非 React 组件上下文中也能使用 context-aware 的 `message`
- 在实例尚未就绪时，再回退到静态 `antd message`

### 5.4 提供 Layout 默认用户区所需字段

当前项目使用 Umi Layout 默认的头像、昵称、退出登录菜单逻辑。

因此在 `getInitialState()` 返回的用户对象中，会额外映射：

- `name = username`
- `avatar = avatar || APP_LOGO`

这里的 `name` 主要是布局适配字段，业务语义仍以 `username` 为准。

## 6. 权限体系说明

文件：`src/access.ts`

当前权限基于 `getInitialState()` 返回的当前用户结果生成。

推荐约定：

- 权限判断逻辑只放 `access.ts`
- 页面中通过框架提供的权限能力消费
- 不要在多个页面里重复写相同权限判断

后续若引入角色、菜单、按钮级权限，建议继续沿用：

- `getInitialState` 获取原始权限数据
- `access.ts` 统一生成权限标记
- 页面只使用权限标记，不直接解析原始权限对象

## 7. 全局状态管理规范

本项目统一使用 `Redux Toolkit + react-redux` 管理运行期的全局状态。

### 7.1 相关文件

```text
src/store/
  index.ts                  store 创建入口
  hooks.ts                  类型化 hooks 封装
  slices/
    uiSlice.ts              UI 运行期状态占位 slice
```

### 7.2 各文件职责

#### `src/store/index.ts`

负责：

- 创建 `store`
- 注册所有 reducer
- 导出 `RootState`
- 导出 `AppDispatch`

#### `src/store/hooks.ts`

负责：

- 导出 `useAppDispatch`
- 导出 `useAppSelector`

作用：

- 避免每个页面重复书写 `useDispatch<AppDispatch>()`
- 避免每个页面重复声明 `RootState`
- 统一多人协作时的 Redux 使用方式

团队约定：

- 页面和组件中统一使用 `useAppDispatch`
- 页面和组件中统一使用 `useAppSelector`
- 不直接使用裸 `useDispatch`、`useSelector`

#### `src/store/slices/uiSlice.ts`

负责：

- 定义运行期 UI 状态结构
- 定义修改状态的 reducers
- 导出 actions 和 reducer

### 7.3 什么时候放到 Redux

建议放入 Redux 的状态：

- 多页面共享状态
- 页面切换后仍需保留的业务状态
- 多个组件都依赖的筛选条件、表格状态、编辑态
- 应用运行中会频繁更新的全局信息

不建议放入 Redux 的状态：

- 单个组件内部临时状态
- 只在一个页面局部使用的弹窗开关
- 表单库本身已管理得很好的局部字段状态

### 7.4 什么时候放到 `getInitialState`

建议放入 `getInitialState` 的数据：

- 应用启动就必须拿到的数据
- 当前用户信息
- 权限基础信息
- 系统基础配置

建议不要把所有业务状态都塞进 `getInitialState`。

一句话区分：

- `getInitialState` 管应用启动初始化与登录用户上下文
- `Redux Toolkit` 管应用运行期共享状态

### 7.5 新增一个 slice 的标准步骤

1. 在 `src/store/slices/` 下新建对应 slice 文件
2. 定义 state 类型和 `initialState`
3. 使用 `createSlice` 编写 reducers
4. 在 `src/store/index.ts` 注册 reducer
5. 在页面中通过 `useAppSelector` 和 `useAppDispatch` 使用

示例目录建议：

```text
src/store/
  slices/
    uiSlice.ts
    userSlice.ts
    tableFilterSlice.ts
```

### 7.6 页面中标准用法

读取状态：

```ts
const siderCollapsed = useAppSelector((state) => state.ui.siderCollapsed);
```

修改状态：

```ts
const dispatch = useAppDispatch();
dispatch(setSiderCollapsed(true));
```

### 7.7 团队协作约定

- 一个业务域一个 slice，避免把所有状态堆进单一 slice
- 当前登录用户不要重复同步进 Redux
- reducers 保持纯粹，只处理状态变更
- 异步请求尽量放在页面逻辑或单独封装，不要把业务逻辑随意散落到多个组件
- 不再新增 `src/models/*`
- 不在业务页面、业务组件中使用 `useModel`
- `config/config.ts` 中保留 `model: {}`，仅用于满足 Umi 框架层的 `initialState/access/layout` 依赖

## 8. 页面开发规范

### 新增页面的推荐步骤

1. 在 `src/pages/` 下创建页面目录
2. 编写页面组件
3. 在 `config/routes.ts` 中注册路由
4. 如需接口调用，在 `src/services/` 下补充服务函数
5. 如需共享状态，在 `src/store/slices/` 下新增 slice 或复用现有 slice

### 页面职责建议

- 页面负责拼装数据和组件
- 复杂展示拆到 `components/`
- 接口请求不要直接散落在多个子组件里
- 跨页面共享状态不要用 props 层层透传

---

## 9. 接口调用规范

目录：`src/services/`

当前项目中 `src/services/demo/` 为示例服务目录。

建议约定：

- 按业务域拆分服务目录
- 一个文件导出一组相关接口
- 类型定义和接口请求放在一起维护
- 页面不要直接拼接接口地址和请求参数结构

### 9.1 请求层当前约定

请求基础设施位于：

- `src/api/requestConfig.ts`
- `src/api/requestErrorConfig.ts`

当前约定如下：

- 基础前缀：`/api`
- 服务层生成代码使用 `/v1/...` 形式路径
- 当前业务成功码暂定为 `10000`
- 业务码 `30007`、`30008` 视为登录失效
- 业务码 `30005` 视为权限不足
- HTTP `401/403/404/422/5xx` 已有统一分支处理

注意：

- 上述业务码仍属于当前阶段临时约定
- 等后端正式确认协议后，应统一抽离为常量并同步接口文档

推荐后续结构：

```text
src/services/
  user/
    index.ts
    typings.d.ts
  order/
    index.ts
    typings.d.ts
```

## 10. 新人接手建议

新同学接手项目时，推荐按下面顺序阅读：

1. `config/config.ts`
2. `config/routes.ts`
3. `src/app.tsx`
4. `src/access.ts`
5. `src/store/`
6. 目标业务页面目录
7. 对应 `services/` 目录

---

## 11. 常见协作规则

- 改页面前先确认路由和权限入口
- 改全局状态前先确认是否已有现成 slice
- 新增共享状态时先判断应放 `getInitialState` 还是 Redux
- 同一份业务状态只保留一个真实来源，避免多处重复维护
- 不要重新引入业务 `Umi model`
- 不要删除 `config/config.ts` 中的 `model: {}`，否则 `initialState/access/layout` 的生成代码可能缺少 `plugin-model`
